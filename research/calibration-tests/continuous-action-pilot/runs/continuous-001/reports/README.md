## 阻断原因

第二阶段任务要求：当一个案例为 `indeterminate` 时，主 `expectations` 必须使用 `status/indeterminate`。冻结 Schema 同时要求这种状态值的 `unit` 必须是 `null`。

但冻结模板把有量纲观察量的单位写成固定值，例如：

- `count`
- `engine_unit`
- `engine_unit_per_second`
- `millisecond`

参与者被要求只实例化占位符，不能改写这些固定元数据。因此，遵守模板得到的“不确定预测”无法满足 Schema。

四席各自独立地产生了同一错误签名：

- `CA-R1`：4 个固定单位错误；
- `CA-R2`：6 个固定单位错误；
- `CA-R3`：10 个固定单位错误；
- 合计：每席 20 个。

只读反事实诊断在内存中把不确定主预测的单位改为 `null` 后，四份回答全部通过响应 Schema；其中 `p02`、`p03`、`p04` 还直接通过回答范围检查。这个修改没有保存，也没有用于装配，因为那会把保管者的修正伪装成参与者提交。

机器检查见：

- [预测模板契约检查](prediction-template-contract-check-v0.1.0.json)
- [阻断事故记录](stage2-template-schema-unit-incident-v0.1.0.json)

## 为什么没有继续替补

`actor-plan.md` 规定，无效回答必须换用新的空白 actor 与会话，并从第一阶段重新开始。这条规则适合处理单个参与者的偶发无效回答。

本次四个独立席位却都命中同一冻结契约冲突。继续替补不能消除它；若向替补者追加 `unit=null` 提示，就改变了参与者材料；若在装配前自动改写回答，就破坏了原始证据。两种做法都会把 `continuous-001` 变成未预注册的新协议。

因此本轮在正式执行前失败关闭。

## 第一阶段同时暴露的可用性问题

第一阶段最终取得了四份有效提交，但 `p01` 和 `p03` 共留下十次无效尝试。主要原因是参与者可见模板没有完整呈现：

- 本地 ID 只允许小写的正则约束；
- `integrity_exposures` 非空时要求对象，而不是字符串。

盲测 actor 又被禁止读取模板所引用的外部 Schema。也就是说，设施知道这些约束，参与者却不一定能从派发材料得知。该问题没有阻断第一阶段，但说明“Schema 可验证”不等于“参与者可以仅凭派发材料构造有效回答”。

## 对理论结论的影响

本轮不能支持或反驳 `CA-01`、`CA-SR 0.1` 或任何候选**原语**：

- 没有有效预测集合；
- 没有正式执行；
- 没有正式结果；
- 没有揭示真值；
- 因而也没有可比较的理论证据。

它只产生一项方法结论：正式盲测包在冻结前必须证明参与者材料覆盖所有 Schema 条件分支，而不能只验证“某个合成有效载荷”。

下一版修复要求见[协议 0.1.1 修复计划](../../../protocol-0.1.1-repair-plan.md)。
